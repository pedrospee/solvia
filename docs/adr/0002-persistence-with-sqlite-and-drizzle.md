# ADR-0002: Persistence with SQLite, better-sqlite3 and Drizzle

- **Status:** Accepted
- **Date:** 2026-09-28
- **Phase:** 2B

## Context

Phase 2B persists the ledger built in Phase 1. Solvia is single-user and local: one process,
one person, a database on their own disk. The persistence layer must never change the meaning of
the financial core: money is `bigint` minor units, rates are exact decimal strings, balances are
derived. The real database holds real financial data, so migrations and restores must never
destroy the only copy.

## Decision

### Engine and libraries

| Choice             | Role                                                                         |
| ------------------ | ---------------------------------------------------------------------------- |
| **SQLite**         | One local file, ACID transactions, no server to run                          |
| **better-sqlite3** | Synchronous driver with prebuilt binaries; supports safe integers (`bigint`) |
| **Drizzle ORM**    | Typed schema and queries, plus the migrator                                  |
| **Drizzle Kit**    | Generates SQL migrations from the TypeScript schema (`npm run db:generate`)  |

Every connection (`openSqlite`) enables `foreign_keys` (SQLite leaves them off by default), uses
the WAL journal for file databases, and turns on safe integers. The server holds one connection
for its lifetime and closes it on shutdown; scripts open and close their own.

### Money and `bigint`

Money is stored as SQLite `INTEGER` (signed 64-bit) and handled as `bigint` end to end. Verified
against drizzle-orm 0.45.3 and better-sqlite3 13.0.3:
- Drizzle's SQLite `integer()` column has no `bigint` mode; its values arrive as `number`, losing
  precision above `Number.MAX_SAFE_INTEGER`.
- `blob({ mode: "bigint" })` stores the digits as text inside a BLOB, not as an INTEGER.
- better-sqlite3 returns `number` by default. With `defaultSafeIntegers(true)` it returns `bigint`
  for every INTEGER value, and binds `bigint` parameters natively.

So money columns use a Drizzle `customType` whose SQL type is `integer` and whose conversions
**throw** unless they receive a `bigint`, on a connection with safe integers enabled. A value
above `Number.MAX_SAFE_INTEGER` makes the round trip `bigint → INTEGER → driver → Drizzle → bigint`
without ever becoming a `number` (covered by a test).

Consequences:
- Safe integers apply to every INTEGER column, so Drizzle's `integer()` (typed `number`) would lie
  at runtime. The schema therefore declares integer columns only with the `bigint` custom type.
- Amounts outside the signed 64-bit range cannot be stored (the driver throws a `RangeError`).
  The API contract rejects them first, with a 400.

### Other values

| Value                                  | SQLite type | Format                                                                             |
| -------------------------------------- | ----------- | ---------------------------------------------------------------------------------- |
| Exchange rate                          | `TEXT`      | Exact decimal string (`"5.882353"`), never `REAL`                                  |
| Business date                          | `TEXT`      | `YYYY-MM-DD`                                                                       |
| `createdAt`, `updatedAt`, `recordedAt` | `TEXT`      | ISO 8601                                                                           |
| Entity id                              | `TEXT`      | `crypto.randomUUID()`, generated by the backend (the core stays free of Node APIs) |

No column is `REAL`.

### Balances are derived, not stored

Balances are calculated by `calculateAccountBalance` from `@solvia/core` over postings loaded from
the database. No balance column exists. For a single user this is fast enough; SQL aggregation may
be introduced later as a performance optimisation, provided it produces the same results as the
domain rule and the core remains the definition of a balance.

### Migrations

- Schema lives in `backend/src/infrastructure/database/schema/`; migrations are generated into
  `backend/src/infrastructure/database/migrations/` and committed.
- **Committed migrations are immutable.** A schema change always creates a new migration.
- `npm run db:migrate` is the only operation that changes the schema. The server and the other
  scripts refuse to run while migrations are pending.
- Pending migrations are detected with the same rule as Drizzle's migrator (generated after the
  last applied one). All pending migrations are applied inside one SQLite transaction, as
  Drizzle's migrator does, with foreign keys turned off around it and checked before commit
  ([ADR-0004](0004-ledger-persistence.md), L6).
- CI runs `db:generate` and fails if it changes the migrations folder: `drizzle-kit check` only
  validates migration files among themselves and does not detect schema drift.

### Backup before migrating

Before applying pending migrations to an existing database, `db:migrate` writes a backup to
`BACKUP_DIR` and verifies it; if either step fails, no migration runs. A database with no pending
migrations, or a brand-new empty one, is not backed up.

Backups use `VACUUM INTO`: it writes a transactionally consistent snapshot (including pages still in
the WAL) and refuses to overwrite an existing file. Verification opens the copy read-only, runs
`PRAGMA integrity_check`, and compares every schema object and every table's row count with the
source.

Manual backup, restore and a complete JSON export are scripts (`db:backup`, `db:restore`,
`data:export`, Phase 2B slice 6). Backups and exports live outside the repository.

## Alternatives considered

| Option                                   | Why not                                                                                                                                                                                |
| ---------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **`node:sqlite`** (built into Node 24)   | No extra native dependency, but drizzle-orm 0.45 has no driver for it, so we would lose the typed queries and migrator or write an adapter. Worth revisiting when Drizzle supports it. |
| **Money as `number`**                    | Loses precision above `Number.MAX_SAFE_INTEGER` and invites floating-point arithmetic.                                                                                                 |
| **Money as `TEXT` or BLOB**              | Exact, but no longer an integer column: sorting, `CHECK` constraints and future SQL aggregation would operate on strings.                                                              |
| **Running migrations at server startup** | Convenient, but a schema change would happen as a side effect of `npm run dev`.                                                                                                        |
| **Stored balances**                      | A second source of truth that can drift from the postings.                                                                                                                             |

## Consequences

- Money never passes through a JavaScript `number`, from the API to the disk and back.
- A schema change is always visible: a new committed migration, applied explicitly, after a
  verified backup.
- After pulling a new migration, `npm run db:migrate` must be run before `npm run dev`.
- Audit history (who changed what) is not part of this design; it is deferred to Phase 12.
